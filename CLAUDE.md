# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

KTower Inventory — an internal warehouse stock dashboard. The entire application is
one file, `index.html` (~1,080 lines), that runs by opening it in a browser.
`inventory.csv` is a static export of the seed data.

Not a git repository. No package manager, no `node_modules`, no Node installed on this
machine.

## Hard constraints

These are requirements of the project, not incidental choices. Violating any of them
breaks the deliverable:

- **Everything stays in `index.html`** — markup, CSS and JS in one file. No build step,
  no bundler, no framework, no `<script src>` / `<link>` to any CDN.
- **No storage APIs.** No `localStorage`, `sessionStorage`, or IndexedDB. State is
  in-memory only and resets on reload — that is intended.
- **No browser dialogs.** No `alert()` / `confirm()`. Confirmations go through
  `toast()`, which writes into the `aria-live="polite"` region `#toastZone`.
- **No inline event handlers.** No `onclick=` attributes; wire everything with
  `addEventListener` in `init()`.

Before finishing any change, confirm none of these crept back in:

```powershell
Select-String -Path index.html -Pattern 'onclick=|localStorage|sessionStorage|alert\(|confirm\(|https?://|<script src|<link' -AllMatches
```

Expect zero matches. (The Google Fonts / cdnjs allowances that apply to published
Artifacts do **not** apply here — this file must work offline from a shared drive.)

## Commands

There is no build, lint, or test tooling. Verification is manual.

```powershell
# Run the app
start index.html

# Verify the CSV parses and its totals still match the app's summary strip
$csv = Import-Csv .\inventory.csv
($csv | Measure-Object -Property Quantity -Sum).Sum   # expect 27134
$csv | Group-Object Status | Select-Object Count,Name # expect 9 / 4 / 1
```

Current seed data should render as: **14 SKUs, 27,134 units, 5 below reorder,
4 warehouses**, with 9 green / 4 amber / 1 red status pills.

## Architecture

The `<script>` block is organised into six commented sections: STATE, HELPERS, RENDER,
FORM VALIDATION, EVENT HANDLERS, INITIALISATION. Keep new code in the matching section.

**`records` is the single source of truth.** Every render derives from it. Never read
application state back out of the DOM, and call `renderAll()` after any mutation —
`renderTable()` and `renderSummary()` are not meant to be called individually except
from filter/sort handlers, which don't change `records`.

**`COLUMNS` drives both the header markup and the sort comparator.** To add or change a
column, edit that one array — `renderHead()` builds the `<th>`s from it and
`getVisibleRecords()` reads `type` / `numeric` from it to pick a comparison. Don't add a
`<th>` by hand; the two will drift.

**Status is computed, never stored.** `getStatus()` runs on every render. Records have no
`status` property, so nothing can go stale. The zero-check must stay first — `0` also
satisfies `qty <= reorder`. Sorting the Status column uses `STATUS_RANK` (severity
order), not alphabetical.

**Summary vs. table scope differ deliberately.** `renderSummary()` reads the full
`records` array; `renderTable()` reads the filtered `getVisibleRecords()`. Filtering the
table must not change the headline totals.

## Traps

**`renderTable()` rebuilds `<thead>` as well as `<tbody>`.** Two consequences:

1. Any element inside the table that holds focus is destroyed on re-render.
   `handleHeadClick` already restores focus to the clicked column button; anything else
   interactive added to a header needs the same treatment.
2. Listeners must be attached to the persistent containers `#tableHead` / `#tableBody`
   and use `event.target.closest(...)` delegation — never to a row, cell, or button
   directly, since those are replaced on every render.

**Rows are built as HTML strings and assigned via `innerHTML`.** Every interpolated
record field must pass through `escapeHtml()`, including inside attributes
(`aria-label`, `data-*`). This applies to seed data too, not just form input.

**`flashId` is a one-shot flag.** `handleSubmit` sets it, the next `renderTable()`
consumes it to add `.is-new`, then clears it. Don't read it expecting persistence.

**Filters are cleared on add when they would hide the new row.** `handleSubmit` checks
this explicitly — without it, a valid submission appears to do nothing. Preserve that
behaviour if the filter logic changes.

**`inventory.csv` is a static snapshot, not generated by the app.** It does not track
adds or deletes made in the browser and will drift from the seed array. If you change
the seed data in `index.html`, regenerate the CSV by hand and re-run the totals check
above. Its `Status` column is a frozen copy of a derived value.

## Formatting conventions

Display formatting lives only in the UI layer — `fmtQty()` (thousands separators) and
`fmtMoney()` (USD, 2dp). Data stays raw: `12500`, not `12,500`. `inventory.csv`
deliberately carries unformatted numbers so spreadsheets read the columns as numeric.

Dates are `YYYY-MM-DD` from `todayISO()`, which uses **local** time, not UTC, so "today"
matches the user's calendar day. That format also sorts lexicographically =
chronologically, which is why Last Updated sorts correctly as plain text.

Quantity and Reorder Level are validated as non-negative **integers**; Unit Cost allows
decimals and is rounded to 2dp on save. SKU uniqueness is trimmed and case-insensitive.

## Accessibility

These are requirements, not nice-to-haves: a `<label for>` on every input; semantic
`<table>` with `<thead>`/`<tbody>`; sortable headers as real `<button>`s carrying
`aria-sort`; field errors linked by `aria-describedby` with `aria-invalid` on the input;
visible `:focus-visible` rings; `role="status" aria-live="polite"` for confirmations.

The design is deliberately single-theme (light). Every colour is painted explicitly from
the `:root` custom properties, so no dark-mode variant is needed or expected.

## Publishing a preview

The page can be published as an Artifact for a shareable live preview. The Artifact host
supplies its own `<!doctype>`/`<head>`/`<body>`, so the file must be unwrapped first —
take from the `<title>` line to just before `</body>`, dropping the `</head>` and
`<body>` lines. Publish the unwrapped copy from the scratchpad; never overwrite
`index.html` with it, and note that the Artifact sandbox blocks page-initiated file
downloads (relevant if a CSV export button is ever added).
